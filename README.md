# dota2-coach

Локальный инструмент: берёт `match_id`, тянет детальные данные матча из OpenDota,
отбирает из них значимое и собирает текстовый промпт. Промпт вставляешь в
ChatGPT/Claude и получаешь разбор игры как от тренера.

Три режима разбора:

* **Один матч** — твоя игра: почему матч пошёл так и что было в твоих руках;
* **Вся игра** — тот же матч без привязки к игроку: почему победила одна сторона,
  кто на самом деле решил игру и что могли сделать проигравшие;
* **Профиль** — последние N матчей игрока сводятся в кросс-матчевую выжимку и
  разбираются на предмет того, что **повторяется**.

После первого промпта по матчу любой его отрезок можно уточнить **коротким
промптом-продолжением** для того же чата — без повторной роли тренера, драфта и
методики, которые модель уже прочитала.

Фундамент собственного replay engine уже доступен отдельно. Команда
`python -m dota2coach replay inspect <путь.dem>` потоково проверяет фиксированный
Source 2 header, лимит размера и SHA-256 файла. Команда
`python -m dota2coach replay scan <путь.dem>` строго проходит весь контейнер без
сохранения payload в памяти и строит первый seek-индекс: диапазон ticks, частоты
команд, compressed frames, `DEM_FullPacket` и границу playback. Protobuf/entity
decoder подключается поверх независимого контракта из `dota2coach/replay/`.

Вывод инструмента — это начало разговора, а не финальный вердикт: модель может
спросить про то, чего в данных нет, и назвать минуты эпизода, который стоит
разобрать поминутно.

Следующий этап превращает генератор промпта в полноценный evidence-driven
тренер: интерактивный обзор матча, собственный движок точного разбора replay и
итеративное исследование конкретных игровых эпизодов. Целевая продуктовая и
техническая рамка описана в
[docs/PRODUCT_VISION_AND_ROADMAP.md](docs/PRODUCT_VISION_AND_ROADMAP.md).
Измерения replay-слоёв ведутся отдельно в
[docs/REPLAY_BENCHMARKS.md](docs/REPLAY_BENCHMARKS.md), чтобы быстрый проход по
контейнеру не выдавался за скорость полного entity decode.

Работает двумя способами — из терминала и через локальную страницу в браузере.
Ни базы, ни истории, ни авторизации: всё живёт на твоей машине.

## Установка

```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
```

Ключ OpenDota не обязателен — API работает и без него, просто с меньшими лимитами.
Если он есть:

```bash
export OPENDOTA_API_KEY=твой_ключ
```

## Запуск: веб-интерфейс

```bash
python -m dota2coach serve
```

Открыть <http://127.0.0.1:8000>. Эквивалент напрямую через uvicorn:

```bash
python -m uvicorn dota2coach.web.app:app --port 8000
```

Не открывай `dota2coach/web/static/index.html` как `file://`: сервер добавляет
переводы и обслуживает API. При прямом открытии страница теперь показывает эту
инструкцию вместо поломанного пустого интерфейса. Если папку проекта переносили
после создания `.venv`, запускай uvicorn через `python -m` как выше либо пересоздай
окружение: исполняемые файлы внутри старого `.venv` содержат абсолютный путь.

Порт можно задать и переменной окружения `PORT` — тогда сервер слушает
`0.0.0.0` (так его запускает Render, см. [Деплой](#деплой-на-render)).

Базовый вид страницы минимальный — ровно то, без чего нельзя: **ID матча, ID
игрока, кнопка** (в режиме «Вся игра» — только ID матча). Всё остальное лежит под
свёрнутым блоком «Расширенные настройки»: роль, фокус, модель, вопрос и уровень.
Глубина в интерфейсе не выбирается — берётся дефолт модели (в API и CLI она
осталась). Веб ничего не пишет в `output/` — файл отдаёт браузер.

После анализа страница превращается в **сессию матча**:

1. **Промпт** — первым, с заголовком матча, кнопками «Копировать» и «Скачать .txt».
2. **«Уточнить момент»** — график перевеса золота/опыта по всему матчу и список
   командных драк. Отрезок выделяется протягиванием по графику, кликом по драке
   (отрезок встаёт вокруг неё с запасом в пару минут) или ползунком под графиком.
   Кнопка «Промпт по отрезку» отдаёт короткое продолжение для того же чата:
   отрезок поминутно и без прореживания, плюс необязательный вопрос про него.
   Матч второй раз не скачивается — уходит тот же ответ OpenDota, что и в первый.
3. **«Подробности матча»** — свёрнуты: сводка игрока, сигналы по бенчмаркам,
   скорборд всех десяти, драфт, сборки и объективы. К ним приходят за
   конкретной цифрой, а не читают подряд.

Что ещё есть на странице:

* **Переключатель режимов** сверху — «Один матч», «Вся игра» и «Профиль». В
  режиме профиля базовые поля становятся `account_id` + число матчей, а фильтры
  по герою и позиции уезжают в расширенные настройки. В режиме «Вся игра» никто
  не помечен как «я»: график показывает перевес Radiant, сигналы по бенчмаркам не
  выводятся.
* **Radiant/Dire** как смысловая метка: результат окрашивается в цвета твоей
  стороны, с бейджем вида «Dire · победа». Акцент интерфейса при этом остаётся
  нейтральным — фракции не раскрашивают всё подряд.
* **Подсказки «?»** у каждого поля — что оно делает и как этим пользоваться.
  Открываются по клику (не по ховеру: ховер недоступен с клавиатуры), закрываются
  по Esc или клику вне.
* **Язык** — русский, английский, украинский. Один селектор переключает и подписи
  интерфейса, и язык генерируемого промпта.
* **Тема** — тёмная по умолчанию, светлая по кнопке. Обе построены как плотное
  аналитическое рабочее пространство; прозрачность оставлена только временным
  overlay-слоям.
* **Роль** — Auto использует эвристику линии/нетворта; явный выбор позиции 1–5
  переопределяет её только для ★ и меняет критерии оценки и приоритет фактов.
* **Role-aware focus** — для саппортов UI не предлагает `farm` как основной
  фокус, а поднимает `vision` и `enable`.
* **Ссылка вместо ID** — в поле матча можно вставить ссылку с Dotabuff, OpenDota
  или STRATZ, номер извлечётся сам.
* **Оценка токенов** — видно, влезет ли промпт в бесплатный чат. Чипы под
  заголовком показывают только то, что что-то сообщает: фокус — если он не
  общий, роль — если её выбрали.
* **Дисклеймер** под результатом: инструмент даёт данные и промпт, качество
  разбора зависит от модели, в которую его вставят.
* **Плейсхолдеры-примеры** в полях: у вопроса к разбору три примера чередуются
  (пока в поле не начали писать), у поля MMR — без лишней серьёзности.
* **Инфо-окно** по кнопке «i» в шапке: что это, что можно делать, что важно
  понимать и три совета. Закрывается крестиком, кликом вне и Esc; фокус заперт
  внутри окна и возвращается туда, откуда открыли.
* **Иконки позиций 1–5** вместо выпадающего списка — компактный сегментированный
  контрол с читаемыми символами обязанностей. Переключается мышью и стрелками с
  клавиатуры.
* **Оценка разбора** под результатом: 👍/👎 и необязательный комментарий.
* **Движение только по делу**: синхронный ползунок отрезка, компактная индикация
  загрузки и короткий отклик «Скопировано ✓». Фон статичен, а при
  `prefers-reduced-motion` необязательные переходы отключаются.

Флаги: `--port 8080`, `--host 0.0.0.0`, `--reload` (автоперезапуск при правках).
По умолчанию сервер слушает только `127.0.0.1` — наружу не торчит.

Форма запоминает язык, тему, режим, состояние «Расширенных настроек»,
account_id, уровень и опции в localStorage, так что при следующем матче меняется
только ID. `Cmd`/`Ctrl`+`Enter` отправляет форму.

## Деплой на Render

Приложение поднимается «с нуля» по git-клону: один сервис отдаёт и страницу,
и API.

**Шаг за шагом:**

1. Запушить репозиторий на GitHub.
2. На Render: **New → Web Service** → подключить репозиторий.
3. Настройки (Render подхватит их сам из [render.yaml](render.yaml), если
   создавать сервис через **New → Blueprint**):
   * **Build Command:** `pip install -r requirements.txt`
   * **Start Command:** `uvicorn dota2coach.web.app:app --host 0.0.0.0 --port $PORT`
   * **Plan:** Free
   * **Health Check Path:** `/healthz`
4. В **Environment** добавить переменные — все опциональны, см. таблицу ниже.
5. **Deploy**. Автодеплой в `render.yaml` выключен намеренно: каждый push в
   master не уезжает на прод сам, катим кнопкой **Manual Deploy**.

`PORT` подставляет сам Render. Приложение видит его и слушает `0.0.0.0`; без
`PORT` (то есть локально) остаётся на `127.0.0.1` — личный инструмент не должен
без спроса торчать в сеть.

### Переменные окружения

Полный список с пояснениями — в [.env.example](.env.example). Ничего секретного
в репозитории нет: ключи вводятся в дашборде Render (`sync: false`).

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `OPENDOTA_API_KEY` | пусто | необязателен; с ключом лимиты OpenDota выше |
| `PORT` | `8000` | задаёт хостинг; его наличие включает `0.0.0.0` |
| `HOST` | авто | если нужно переопределить биндинг вручную |
| `PARSE_TIMEOUT_SEC` | `180` | сколько ждать парсинг матча; на хостинге ставь `60` |
| `DOTA2COACH_CACHE_DIR` | `.cache` | куда складывать кэш ответов API |
| `FEEDBACK_FILE` | `feedback.jsonl` | файл с отзывами |
| `FEEDBACK_WEBHOOK_URL` | пусто | если задан — отзывы дублируются POST-ом туда |

### Что учтено для free-tier

* **Холодный старт.** Справочники OpenDota (восемь ресурсов через общий
  rate-limiter) греются фоновым потоком при старте, а не первым посетителем.
  Сам подъём уснувшего контейнера это не ускоряет — Render усыпляет free-сервис
  после ~15 минут простоя, и первый запрос после сна ждёт старт.
* **Эфемерная файловая система.** Кэш и файл отзывов живут до перезапуска. Код
  от них не зависит: кэш — оптимизация, отзывы дублируются в лог и вебхук.
  Каталог, недоступный для записи, приложение не роняет.
* **Долгие запросы.** Ожидание парсинга ограничено `PARSE_TIMEOUT_SEC`: за
  обратным прокси соединение оборвут раньше, чем мы ответим, и пользователь
  увидит пустую ошибку вместо объяснения.
* **Диагностика сбоев источника.** Страница показывает локализованный текст,
  выбранный по `kind`, — по нему не отличить исчерпанный лимит от блокировки
  клиента или HTML-заглушки вместо JSON. Поэтому каждый сбой источника пишется
  в лог сервиса строкой `dota2coach: сбой источника [kind] ...` с кодом ответа,
  `Content-Type` и началом тела. Если на проде видно «OpenDota недоступна» —
  причина в логах Render, а не в догадках.
* **Матчи качает браузер, а не сервер.** Лимит OpenDota считается **по IP**:
  60 запросов в минуту, около 3000 в сутки. Бесплатные контейнеры Render выходят
  в сеть через общие адреса, одни на множество чужих сервисов, и их суточный
  лимит выбирают другие — сервер получал 429 на первом же запросе, и сайт был
  мёртв при исправном коде. OpenDota разрешает CORS, поэтому страница сама
  забирает `/matches/{id}` (и при необходимости заказывает парсинг), а для
  профиля — список матчей и сами матчи, со своего IP и в пределах своего лимита.
  Серверу уходит готовый ответ (`raw_match` / `raw_matches` в запросе).

  Сервер по-прежнему умеет сходить сам: если браузер ничего не прислал, работает
  прежний путь. Присланным данным сервер доверяет только в рамках одного запроса
  — в общий кэш они не пишутся, иначе один пользователь мог бы подложить
  подправленный матч остальным. Для профиля страница сначала спрашивает у
  сервера план (`GET /api/profile/plan`): переводить имя героя в id умеют только
  справочники сервера.
* **Справочники с зеркала.** Герои, предметы и способности тянутся с OpenDota,
  а при отказе — из `odota/dotaconstants` на GitHub: OpenDota собирает свои
  `/constants` ровно оттуда, формат тот же, лимита OpenDota там нет. Без этого на
  забитом IP герои превращались в «hero_5».
* **Вежливость к OpenDota.** На серверном пути лимит **общий на всех**
  пользователей сервиса, поэтому rate-limiter один на процесс, потокобезопасен,
  и разборы сериализуются. Браузер качает матчи профиля не больше четырёх
  одновременно.

## Отзывы

Под каждым разбором — 👍/👎 и необязательный комментарий. Оценка уходит сразу
по клику (комментарий пишут единицы, а ждать «Отправить» значит терять голос),
комментарий досылается отдельной записью с `followup: true` — чтобы при подсчёте
один человек не считался дважды.

**Персональных данных не собираем:** `account_id` в отзыв не кладётся. В записи
только оценка, комментарий и настройки разбора: режим, `match_id`, роль, depth,
focus, модель, язык, размер промпта, время.

Отзыв уходит сразу в три места (сбой одного не мешает остальным):

```
stdout ── всегда, первым. Единственный канал, переживающий перезапуск контейнера
файл ──── FEEDBACK_FILE, по умолчанию feedback.jsonl (локально — архив)
вебхук ── если задан FEEDBACK_WEBHOOK_URL
```

**Как смотреть отзывы на Render:** вкладка **Logs**, фильтр по слову `FEEDBACK`.
Каждая строка — готовый JSON:

```
FEEDBACK {"rating": 1, "mode": "match", "lang": "ru", "model": "chatgpt", ...}
```

Локально то же самое лежит в файле:

```bash
cat feedback.jsonl
```

Файл на хостинге исчезнет при перезапуске — это не баг, а свойство эфемерной
ФС. Если отзывы нужно хранить долго, задай `FEEDBACK_WEBHOOK_URL` (Google Apps
Script, Formspree, свой эндпоинт): это единственный способ, не поднимая базу.

## Запуск: CLI

### Native Replay Engine (C++)

Высокоточный replay parser развивается как отдельное C++17-ядро, а Python
приложение запускает его через ограниченный subprocess. Локальная сборка не
требует внешних библиотек:

```bash
make -C replay_engine test all
python -m dota2coach replay decode replay-cache/match.dem --json
```

Первый native slice уже выполняет mmap/framing, Snappy, protobuf wire validation
и framing внутренних network messages. Send tables, serializers и entity deltas
— следующий слой; текущая команда честно не выдаёт их за готовые координаты или
события. Путь к отдельно установленному бинарю можно задать переменной
`DOTA2_REPLAY_ENGINE_BIN`.

```bash
python -m dota2coach analyze 8931432366 --me 123456789
```

Не знаешь свой `account_id` — укажи героя, которым играл:

```bash
python -m dota2coach analyze 8931432366 --hero "Phantom Lancer"
```

Результат: `output/<match_id>.txt`. Скопируй файл целиком и вставь в чат с LLM.

Если матч ещё не распарсен OpenDota, инструмент сам закажет парсинг и подождёт
(до 3 минут), а потом перезаберёт данные.

## Роль: `--role`

`--role 1|2|3|4|5` задаёт обязанности именно твоего игрока. Без флага всё
работает как раньше: позиция определяется по линии и нетворту.

```bash
python -m dota2coach analyze 8931432366 --hero "Phantom Lancer" --role 1
```

| Значение | Роль | Главные критерии |
|---|---|---|
| `1` | Carry | CS@10, GPM, нетворт, предметы, урон, поздние смерти |
| `2` | Mid | темп, руны, XPM, ранний импакт, участие |
| `3` | Offlane | инициация, фронтлайн, пространство, полученный урон |
| `4` | Soft Support | роуминг, стаки, вижн, контроль, ассисты, utility |
| `5` | Hard Support | вижн/детект, стаки, лечение, ассисты, командные предметы |

Для позиций 3–5 смерть не считается ошибкой автоматически: scaffold требует
проверить, дала ли она инициацию, выгодный размен или спасение кора. Для
саппортов CS/GPM не используются как критерии успеха. OpenDota не даёт надёжного
счётчика save events, поэтому prompt использует лечение, участие в боях и
защитные предметы как свидетельства и запрещает выдумывать число сейвов.

## Режимы

Три параметра — роль, глубина и фокус — решают, как оценивать игрока и какие
факты поднять в промпте.

**`--depth quick|deep`** — сколько подробностей. `quick` (по умолчанию) даёт
скелет матча: драфт, скорборд, бенчмарки, перевес команд, мои предметы и раскачку,
лайнинг, сводку боёв. `deep` разворачивает это на все десять игроков.

**`--focus full|laning|fights|farm|draft|vision|tempo|initiation|enable`** —
под какой вопрос затачивается разбор.
Фокус не только раскрывает профильную секцию, но и приглушает остальные, а заодно
задаёт модели акцент внутри разбора по стадиям.

Новые role-aware фокусы:

* `vision` — obs/sen, деварды, детект и информация вокруг объективов;
* `tempo` — руны, ранние киллы/участие, выход с линии, первые тайминги;
* `initiation` — входы в бой, контроль, поглощённый урон и пространство;
* `enable` — стаки, вижн, лечение, участие и командные/защитные предметы.

```bash
python -m dota2coach analyze 8931432366 --hero "Phantom Lancer" --depth quick --focus laning
```

Порядок величин на 54-минутном матче:

| | full | laning | fights | farm | draft |
|---|---|---|---|---|---|
| **quick** | 15 КБ | 11 КБ | 29 КБ | 18 КБ | 13 КБ |
| **deep** | 38 КБ | 14 КБ | 36 КБ | 24 КБ | 16 КБ |

`--focus fights` тяжелее остальных намеренно: это поимённая раскладка каждого боя,
ради которой флаг и существует.

## Промежуток под лупой: `--window` и `--followup`

«Разбери мне 30–40» — отдельный запрос, для которого поднимать глубину целиком
было бы расточительством.

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --window 39-44
```

Окно — не секция поверх остального, а **перераспределение внимания**: выбранный
промежуток печатается с максимальной детализацией, а весь остальной матч
ужимается до сводки. Иначе детализация окна утонула бы в общем объёме.

Внутри окна экономии нет сознательно:

* все десять героев поминутно, без прореживания — нетворт, опыт, добивания/денаи;
* убийства с таймингами;
* покупки **включая расходники** — по ним видно, кто готовился к бою, а кто фармил;
* задевшие окно бои поимённо;
* объективы.

Пустое окно печатается как факт («отрезок был пустым»), а не пустой секцией:
иначе модель начнёт достраивать события. В `ОГРАНИЧЕНИЯХ ДАННЫХ` появляется
оговорка, что остальные секции сжаты, — чтобы модель не выдавала за факт то, чего
в промпте нет.

Единственное исключение из сжатия — блок отклонений: из него строятся гипотезы, и
он нужен целиком независимо от разбираемого отрезка.

**`--followup`** превращает окно в **промпт-уточнение** для чата, где уже идёт
разбор этого матча. В нём только отрезок — без роли тренера, драфта, картины
матча и методики: модель всё это уже прочитала выше. Короткая задача («разбери
этот отрезок: что произошло, что было в руках игрока, что можно было иначе»)
плюс необязательный вопрос из `--note`. Такой промпт в 3–4 раза короче полного.

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --window 28-36 --followup --note "почему проиграли эту драку"
```

Без `--window` флаг `--followup` не имеет смысла и отклоняется.

## Разбор игры целиком: `--game`

```bash
python -m dota2coach analyze 8931432366 --game
```

Ни `--me`, ни `--hero` не нужны: разбирается матч, а не игрок. Вопросы у такого
разбора свои — как шла игра, почему победила эта сторона, **кто на самом деле
решал игру** и что могла сделать проигравшая сторона.

Главная ловушка здесь — «MVP тот, у кого больше всего урона». Чтобы модель в неё
не попадала, в картине матча для каждого героя заранее посчитано то, по чему
видно влияние: доля нетворта и урона в команде, урон по строениям, смерти и
сколько из них в драках, в скольких драках герой участвовал и откуда брал золото
(строения и Рошан — давление на карту, герои — драки, крипы — фарм). Принцип
методики прямо говорит: много урона в проигранных драках и мало урона у героя,
который выигрывал карту давлением, — обычное дело.

Перевес везде считается с позиции Radiant, роль не подставляется, секции «про
моего игрока» (роль, лайнинг, урон, баффы) скрыты. Работают `--model`, `--lang`,
`--note`, `--focus draft` и окно с `--followup`.

## Режим «Профиль»: кросс-матчевый разбор

Один матч отвечает на вопрос «что случилось». Десяток матчей отвечает на более
полезный: «что у меня повторяется».

```bash
python -m dota2coach profile 123456789 -n 10
python -m dota2coach profile 123456789 -n 10 --hero "Phantom Lancer"
python -m dota2coach profile 123456789 -n 10 --role 5
```

Результат: `output/profile_<account_id>_<N>.txt`. Базы данных нет — агрегация
живёт в памяти на время запроса.

**Полных данных матчей в промпте нет намеренно.** Десять распарсенных матчей — это
сотни килобайт, в которых утонет любая модель. Наружу уходит только выжимка:

| Секция | Что в ней |
|---|---|
| `ВЫБОРКА` | сколько матчей вошло из запрошенных, какие фильтры |
| `СРЕДНИЕ ПО ВЫБОРКЕ` | винрейт, GPM/XPM/CS@10/нетворт, KDA, участие, лайн-эффективность, худший матч по смертям как контекст к среднему |
| `ТРЕНДЫ ПЕРЦЕНТИЛЕЙ` | средний перцентиль, разброс и направление (свежие матчи против старых), а не перцентиль каждого матча |
| `ПОВТОРЯЮЩИЕСЯ ОТКЛОНЕНИЯ` | главный материал разбора, см. ниже |
| `ПРОФИЛЬ ПО СТАДИЯМ ИГРЫ` | на каких пятиминутках перевес уходит систематически |
| `СОСТАВ ВЫБОРКИ ПО ГЕРОЯМ` | без него средние читать нельзя |
| `МАТЧИ ВЫБОРКИ` | по ОДНОЙ строке на матч — достаточно, чтобы сослаться на конкретную игру |

**Повторяющиеся отклонения.** Паттерн — это отклонение, случившееся не однажды
(порог: 40% выборки и минимум дважды). Считается по тому же детектору, что и в
одиночном разборе, поэтому отдельного списка «типичных ошибок» здесь нет и не
будет — он устарел бы так же, как список важных предметов.

**Профиль по стадиям** отвечает на «стабильно проседаю на 25–35 мин»: для каждой
пятиминутки берётся *изменение* перевеса по золоту и усредняется по выборке.
Уровень перевеса для этого не годится — он тянется из предыдущих стадий, и провал
в мид-гейме выглядел бы как провал во всём лейте.

Отдельно защита от вымысла: поминутные ряды есть только у распарсенных матчей,
поэтому стадии часто опираются на меньшую выборку, чем профиль. Если таких матчей
меньше двух, слово «систематически» не употребляется вовсе — печатается таблица и
честная оговорка. Иначе промпт предлагал бы модели вывести закономерность из
одного наблюдения.

**Вежливость к OpenDota.** Матчи тянутся по одному через общий rate-limiter
(~1 запрос/сек), так что 10 матчей — это порядка 15 секунд. Парсинг
нераспарсенных матчей **не заказывается**: десять ожиданий по три минуты
превратили бы запрос в получасовой. Недоступный матч пропускается, а не рушит
профиль; сколько матчей реально вошло, видно и в промпте, и в ответе API.

Фильтр по позиции работает с оговоркой: серверный фильтр OpenDota знает только
линию, а позиция — наша эвристика, поэтому часть скачанных матчей отбрасывается.
Фильтр по герою терпим к вводу (`pl`, `phantom lancer`), но неоднозначное имя
отвергает с просьбой уточнить, а не берёт молча первого подходящего.

Работают `--model`, `--lang`, `--mmr`, `--note` — так же, как в одиночном разборе.

## Что промпт заставляет модель делать

Промпт — это не «вот данные, разбери». В него вшита методика: как думать и в
каком виде отвечать. Обычный игрок получает разбор уровня power-user, ничего не
зная о промптинге.

Раньше правил было больше двадцати, а разделов ответа — десять. Большинство
правил появлялись заплатками на нехватку данных («не вини за фарм», «не
утверждай про BKB»), и модель тратила внимание на соблюдение запретов, а ответ
превращался в простыню, где главное тонуло. Теперь недостающее **посчитано
заранее** в секции `КАРТИНА МАТЧА`, а в методике остались принципы — и ни
одного примера с конкретным героем: ошибок в доте бесконечно много, и любой
пример модель начинает искать там, где его нет.

### Картина матча

Секция, ради которой модель раньше гадала:

* ранг и размер пати (соло-игроку не советуют то, что требует координации);
* счёт, доля нетворта и урона игрока в команде;
* пары по ролям — сколько заработал каждый к 10/20/30 минуте и итоговый нетворт;
* откуда шло золото у игрока и его визави: герои, крипы, нейтралы, строения,
  Рошан, руны, потери при смерти;
* каждая смерть: время, кто убил, была ли это драка, сколько лежал;
* полученный урон по типам, доля урона, от которой BKB не защищает, и главные
  источники.

### Семь принципов

1. **Два вопроса, не смешивая.** Почему игра пошла так — на уровне матча и обеих
   команд. И отдельно — что было в руках игрока и изменило бы это исход. Честный
   ответ «максимум игрока здесь исход не менял» допустим.
2. **Данные — для фактов, знание игры — своё.** Механику героев и предметов
   модель применяет свободно, но привязывает к событиям матча. Поиск в интернете
   не требуется.
3. **Причина перед виной.** В проигранной позиции плохо выглядит всё; цена
   показателя зависит от роли; в драках важно, кто в них участвовал.
4. **Билд — через «выжить и нанести урон».** Кору нужно выжить в драках, где он
   нужен, и успеть там нанести урон; саппорту — выжить и сделать свою работу.
   Модель смотрит, чего не хватало в конкретные моменты, и закрывала ли это
   сборка.
5. **Драфт — по смыслу героев**, а не по спискам винрейтов: что делает каждый
   герой, против чего слаб по механике, как сходятся линии. Пик оценивается по
   тому, что было видно в момент выбора.
6. **Советы, которые игрок делает своими руками.**
7. **Коротко, главное первым**, без пересказа данных.

### Пять разделов ответа

**Почему игра пошла так** → **Что было в твоих руках** (насколько исход зависел
от игрока, что он мог сделать и чего максимум мог добиться) → **Главные
наблюдения** (2–3, только то, что повлияло) → **На следующую игру** (одно
действие) → **Что уточнить** (только если без этого вывод шаткий; сюда же — минуты
эпизода, который стоит разобрать промптом по отрезку). С `--note` первым идёт
ответ на вопрос игрока, с `--focus draft` — подробный разбор драфта.

### Статистически необычное в данных

Чтобы наблюдения не выродились в общие места, промпт содержит секцию
`СТАТИСТИЧЕСКИ НЕОБЫЧНОЕ В ДАННЫХ` — отклонения, найденные автоматически. Это
подсказка, где посмотреть, а не обязательный список: разбирать каждое отклонение
модель не обязана.

Ключевое решение: **никакого списка «важных предметов» или «типичных ошибок»**.
Такой список пришлось бы вести руками, и он всё равно отставал бы от патча и
матчапа. Вместо этого ищутся отклонения в самих данных:

| Что ищем | Как |
|---|---|
| Предмет отстаёт от темпа сборки | ожидаемая минута выводится из накопленной стоимости и GPM, но значимо только превышение над **медианой** отставания по всей сборке |
| Перцентили у краёв | ≤20 или ≥80 для этого героя; низких показываем до трёх, высоких — один |
| Разрыв между метриками | «одно вытянуто, другого нет» |
| Провал в доходе | участок, где GPM просел против личного среднего |
| Кластер смертей | несколько смертей в узком окне — это один эпизод, а не разрозненные ошибки |
| Доля времени мёртвым | против медианы остальных игроков матча |
| Разрыв лайн-эффективности | против соперников по линии |
| Участие в убийствах | на краях распределения |
| Быстрый разворот перевеса | окно, где команда потеряла больше всего относительного золота |

Медиана в первом пункте — важная деталь: без неё у саппорта с вардами и выкупами
флагом помечался бы каждый предмет подряд. Сравнение идёт **с собственной**
сборкой, поэтому «поздний BKB» всплывает сам, как следствие, а не как отдельное
захардкоженное правило.

Каждое отклонение помечено осью (`билд`, `фарм`, `файты`, `линия`,
`позиционирование`) — подсказка, к какой гипотезе его цеплять. Оценок нет: наружу
идёт факт и его контекст. Если отклонений не нашлось, это печатается явно — иначе
модель начнёт додумывать аномалии, которых в данных нет.

## Свой вопрос к разбору: `--note`

Если хочешь разобраться в чём-то конкретном, а не получить обзор «по всем фронтам»,
передай вопрос текстом (у флага есть псевдоним `--ask`):

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --note "почему я так поздно собрал Manta и стоило ли идти в Diffusal?"
```

Что меняется в промпте:

* появляется отдельная секция `## ГЛАВНЫЙ ЗАПРОС ИГРОКА` с твоим текстом;
* первым правилом методики становится «вопрос игрока — главный приоритет»;
* в структуре ответа первым добавляется раздел 0 — ответ на твой вопрос;
* в шапку добавляется указатель на этот блок.

Заметка **не меняет объём промпта** — только приоритет разбора. Отбор фактов
по-прежнему задаётся `--depth` и `--focus`, поэтому вопрос про лайн логично
сочетать с `--focus laning`:

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --focus laning --note "почему я слил лайн против Pudge + Hoodwink?"
```

Без флага структура ответа остаётся из пяти разделов, без нулевого. Пустая строка
(`--note ""`) считается отсутствием заметки. В режиме профиля заметка работает
точно так же.

## Уровень игрока: `--mmr`

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --mmr "Legend 3500"
```

Принимается и число, и название бракета. Если указан, модель получает прямое
указание калибровать советы под этот уровень: предлагать то, что на нём реально
исполняется, а рекомендуя приём выше уровнем — объяснять, зачем он.

## Под какую модель: `--model`

Данные и методика одинаковы для всех, отличается только упаковка.

| `--model` | Обёртка | Глубина по умолчанию |
|---|---|---|
| `chatgpt` (по умолчанию) | markdown | `quick` |
| `claude` | XML-теги `<role>`, `<match_data>`, `<player_question>`, `<method>`, `<output_format>` | `deep` |
| `gemini` | markdown | `deep` |

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --model claude
```

Claude заметно надёжнее держит границы «данные / вопрос / инструкция», когда они
размечены тегами. Дефолтная глубина — подсказка, а не правило: явный `--depth`
всегда важнее.

## Язык промпта: `--lang`

`ru` (по умолчанию), `en`, `uk`. Переключает **весь** промпт — заголовки, подписи
внутри строк, ограничения и методику, — включая указание модели отвечать на этом
языке. В вебе язык интерфейса и язык промпта переключаются одним селектором.

```bash
python -m dota2coach analyze 8931432366 --me 123456789 --lang en
```

Новый язык добавляется одним файлом в [dota2coach/i18n/](dota2coach/i18n/) —
скопировать `ru.py`, перевести значения, добавить код в `_MODULES`. Офлайн-тест
проверит, что ни один ключ не забыт.

## Прочие флаги

`--no-cache` — не брать матч из локального кэша, сходить в API заново. Сыгранный
матч не меняется, поэтому распарсенный ответ кэшируется в `.cache/`: это
экономит запросы, когда гоняешь один матч в разных режимах. Базовый неполный
ответ тоже сохраняется как аварийная копия: в штатном режиме приложение пытается
обновить его, а при временном сбое OpenDota отдаёт честный partial-разбор вместо
пустой ошибки. GET-запросы автоматически повторяются при единичном сетевом
сбое, `429` или `5xx`; ожидание ограничено.

## Как это устроено

```
            CLI            веб-страница
             │                   │
             └──────► core ◄─────┘
                       │
DataSource ──► Normalizer ──► FeatureExtractor ──► BundleBuilder ──► текст
(OpenDota)     (Match)        (Features)           (промпт)
                  │                 ▲                   ▲
                  │                 └─── Policy ────────┘
                  │      (--role / --depth / --focus / --note / --window)
                  │
                  └──► ProfileAggregator ──► ProfileBundleBuilder ──► текст
                       (ProfileFeatures)      (мульти-матч промпт)
```

CLI и веб — две тонкие обёртки над `core.generate_prompt()` и
`core.generate_profile_prompt()`. Генерация живёт в одном месте, поэтому обёртки
не могут разъехаться. Оба режима переиспользуют один детектор отклонений: в
профиле «паттерн» — это просто отклонение, встретившееся не однажды.

| Модуль | Ответственность |
|---|---|
| [`core.py`](dota2coach/core.py) | сборка конвейера, `generate_prompt()` и `generate_profile_prompt()` — точки входа для обеих обёрток |
| [`config.py`](dota2coach/config.py) | единственное место, где читается окружение: биндинг, кэш, таймауты, ключ |
| [`feedback.py`](dota2coach/feedback.py) | плагинное хранилище отзывов: stdout, JSONL, вебхук |
| [`anomalies.py`](dota2coach/anomalies.py) | поиск статистических отклонений — сырьё для гипотез модели |
| [`profile.py`](dota2coach/profile.py) | кросс-матчевая агрегация: средние, тренды, повторяющиеся паттерны, стадии |
| [`scaffold.py`](dota2coach/scaffold.py) | методика разбора: правила для модели и структура ответа |
| [`render.py`](dota2coach/render.py) | упаковка под модель (markdown / XML) и дефолтная глубина |
| [`i18n/`](dota2coach/i18n/) | все тексты проекта — и промпта, и интерфейса |

### API

`POST /api/analyze` принимает `{match_id, account_id, hero, role, depth, focus,
model, lang, note, mmr, window_start, window_end, raw_match, followup,
whole_game}` и возвращает
`{prompt, filename, size_bytes, role, parsed, side, win, window, warning,
overview, …}`. `overview` — versioned data-contract для интерфейса: качество и
гранулярность источника, перспектива игрока, скорборд, поминутные ряды,
объективы, драфт, тимфайты и безопасные benchmark-сигналы без причинного ярлыка.
`role: null` означает автоэвристику, `role: "1"…"5"` — явное переопределение
позиции своего игрока. `depth: null` означает «взять дефолт модели». Окно
передаётся двумя числами, а не строкой «30-40», чтобы его валидировал pydantic, а
не разбор текста; `side` и `win` нужны интерфейсу для фракционной окраски
результата. `followup: true` вместе с окном возвращает короткий промпт-уточнение
(без окна флаг игнорируется). `whole_game: true` разбирает матч без привязки к
игроку: `account_id` и `hero` не нужны, роль не применяется, а в `overview`
появляется `perspective.neutral: true` — никто не помечен как `is_me`, перевес
считается с позиции Radiant, сигналов по бенчмаркам нет. `raw_match` — ответ
OpenDota, уже скачанный браузером.

`POST /api/profile` принимает `{account_id, matches, hero, role, model, lang,
note, mmr}` и возвращает `{prompt, filename, size_bytes, analyzed, requested,
unparsed, winrate, warning, …}`. У него своё окно таймаута: выборка тянется
дольше одиночного разбора.

`POST /api/feedback` принимает `{rating, mode (match | game | profile), lang, model, comment, match_id,
role, depth, focus, window, matches, prompt_bytes, followup}` и отвечает `202`.
`rating` — только `1` или `-1`; длина комментария ограничена; есть потолок
отзывов в минуту на процесс (эндпоинт публичный, а за ним логи и чужой вебхук).
`account_id` эндпоинт не принимает вовсе.

`GET /healthz` — проба живости для хостинга: отвечает сразу, в сеть не ходит,
показывает, прогрелись ли справочники.

Схема — на <http://127.0.0.1:8000/api/docs>.

Блокирующие запросы к OpenDota уходят в пул потоков, поэтому сервер не залипает
на время парсинга. Коды ошибок: 404 — матча нет, 400 — не опознан игрок (в ответ
приходит список героев матча с их account_id), 429 — лимит OpenDota, 502 — сеть,
504 — матч всё ещё парсится. Для профиля добавляются 404 «нет матчей под фильтры»
и 400 «имя героя неоднозначно». Если матч распарсен не полностью, промпт всё равно
возвращается, но с предупреждением в поле `warning`; в профиле `warning` сообщает
о неполных данных или о недоборе выборки.

Для текущих обзорных источников граница проходит по `DataSource`. Полный replay
слишком богат, чтобы ужать его до этого контракта: будущий Replay Intelligence
Engine получит своё каноническое хранилище и query API, а совместимая проекция
из него продолжит возвращать нынешний компактный `Match`. Благодаря этому
`FeatureExtractor`, `BundleBuilder` и CLI сохранят обратную совместимость, а
точные deep-dive сценарии смогут обращаться к replay-данным без потери деталей.

### Replay Engine: первый слой

```bash
python -m dota2coach replay inspect /path/to/match.dem
python -m dota2coach replay scan /path/to/match.dem --json
```

`scan` читает replay одним проходом и с ограниченной памятью. Он проверяет
16-байтовый `PBDEMS2` header, каждый `uvarint32` и размер payload, точность
служебных offsets и усечённые кадры. Неизвестные command ID не теряются, а идут
в coverage-счётчик. На этом этапе payload намеренно не распаковывается и не
трактуется как Dota-события: следующий слой — изолированный protobuf/Snappy
decoder adapter, который будет выбран benchmark'ом на реальных `.dem`.

Что именно попадает в промпт, из какого поля OpenDota и в каком режиме — в
[docs/FEATURE_SPEC.md](docs/FEATURE_SPEC.md). По какому дизайн-коду собрана
страница — в [docs/DESIGN_SYSTEM.md](docs/DESIGN_SYSTEM.md): приёма, которого
нет в том документе, на странице быть не должно.

## Проверка без сети

```bash
python tests/selftest_offline.py
```

Гоняет синтетический матч через весь конвейер и проверяет узкие места: срезание
шаблонов талантов, поглощение компонентов предметов, фильтр нулевых баффов,
определение сгруппированного драфта, компактность `quick` относительно `deep`,
наличие guardrails и разделов ответа, приоритет заметки, совпадение данных между
markdown- и XML-упаковкой, полноту всех трёх словарей и отсутствие русских строк
в английском промпте. Дополнительно сравнивает carry и hard support на одном
матче: role override, набор метрик, правила смертей, role-aware бенчмарки и новые
`vision/tempo/initiation/enable` focus.

Проверяются и новые механики:

* **детектор темпа сборки** — что предмет ловится по отставанию от *собственного*
  темпа, а сборка, целиком сдвинутая на 10 минут (типичный саппорт с вардами), не
  порождает ни одной аномалии;
* **окно** — разбор `--window`, отказ от некорректных границ, максимум внутри окна
  и сжатие всего остального до сводки;
* **профиль** — что единичное отклонение не становится паттерном, что тренд не
  объявляется на трёх матчах, что стадии видят провал после 25-й минуты, и что в
  мульти-матч промпт **не утекли** полные данные матчей;
* **защита от вымысла** — если поминутные ряды есть у одного матча, слово
  «систематически» в промпте не появляется.
