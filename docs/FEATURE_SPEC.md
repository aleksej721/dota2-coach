# FEATURE_SPEC — что попадает в промпт и откуда берётся

Карта соответствий: **сигнал → точное поле OpenDota → тир → в каких режимах печатается**.

Документ описывает то, что реализовано, а не пожелания. Если поля нет здесь —
его в промпт не отдают, даже если OpenDota его возвращает (см. раздел
[Сознательно не экспортируем](#сознательно-не-экспортируем)).

## Принцип отбора

Из OpenDota вытаскиваем максимум, но **экспортируем отобранное**. Причина
простая: промпт на 50 КБ размывает внимание LLM и жжёт токены, а половина этого
объёма — компоненты предметов, дампы нетворта десяти игроков и нулевые счётчики.
Рядом с сырым числом держим его перцентиль там, где OpenDota его даёт.

## Тиры

| Тир | Что это | Где печатается |
|---|---|---|
| **S** | Скелет матча: без этого разбор невозможен | всегда |
| **A** | Детали: все 10 игроков, поминутные ряды, поимённые раскладки | `--depth deep` либо профильный `--focus` |
| **B** | Редко нужное: APM, пинги, max_hero_hit | только `--depth deep` |

## Уровни детализации

Каждой секции `Policy` (см. [policy.py](../dota2coach/policy.py)) назначает уровень
0–3. Это единственное место, где принимается решение «показывать / не показывать»:

| Уровень | Название | Смысл |
|---|---|---|
| 0 | `HIDDEN` | секции нет в промпте |
| 1 | `SUMMARY` | сводка: мои данные + командные агрегаты |
| 2 | `EXPANDED` | все 10 игроков, поминутные ряды, поимённые раскладки |
| 3 | `FULL_LOG` | сырая последовательность (полный лог покупок, содержимое тайм-окна) |

Есть одна ось, которая меняет уровни всех секций сразу, — тайм-окно `--window`,
см. [Тайм-окно](#тайм-окно---window).

## Скаффолд: методика разбора

Живёт в [scaffold.py](../dota2coach/scaffold.py), тексты — в
[i18n](../dota2coach/i18n/). Из OpenDota не приходит, но именно он определяет,
получит игрок разбор или вежливую воду.

В промпт уходят два блока.

**`## КАК ГОТОВИТЬ РАЗБОР` — правила.** Порядок не случайный: сверху то, что
нарушается чаще всего.

| Правило | Ключ i18n | Когда добавляется |
|---|---|---|
| Вопрос игрока — главный приоритет | `method.note_priority` | только с `--note` |
| Оценивать по обязанностям позиции, а не carry-шаблону | `method.role.1`…`method.role.5` | когда роль выбрана или уверенно определена |
| Разобрать каждое отклонение — объяснить либо честно отвергнуть | `method.anomalies` | всегда |
| Это начало разбора, а не финальный вердикт | `method.dialogue` | всегда |
| Каждое утверждение — с числом или таймингом | `method.evidence` | всегда |
| Общие советы вне этого матча запрещены | `method.no_generic` | всегда |
| Сортировка по цене ошибки, а не по времени | `method.impact_first` | всегда |
| Объяснять механизм, а не выдавать правило | `method.explain_why` | всегда |
| Сильные стороны — так же конкретно, как ошибки | `method.balance` | всегда |
| Не хватает данных — сказать прямо | `method.no_invention` | всегда |
| Калибровка под уровень игрока | `method.calibrate` | только с `--mmr` |
| Отвечать на выбранном языке | `method.language` | всегда |

Замыкает блок строка `method.focus` — акцент разбора, выбранный `--focus`. Раньше
фокус разворачивался в список из 4–5 вопросов; с появлением жёсткой структуры
ответа это стало дублированием, поэтому от него остался один акцент на фокус.

**`## ФОРМАТ ОТВЕТА` — структура.** Разделы в фиксированном порядке:

| Раздел | Что требуется |
|---|---|
| 0. Ответ на главный запрос | только с `--note`: прямой ответ с цифрами |
| 1. Вердикт | 2–3 строки: как сыграл + ОДНА главная вещь к исправлению |
| 2. Что получилось хорошо | 1–2 пункта с числами |
| 3. Главный leak | самая дорогая проблема + цепочка «что произошло → во что обошлось» |
| 4. Разбор по стадиям | в порядке важности, не хронологически |
| 5. Что делать дальше | 2–4 измеримых действия с числом для самопроверки |
| 6. Гипотезы | 2–3 **конкурирующие** версии причины исхода из разных областей; для каждой — доказательство, способ проверки и степень уверенности |
| 7. Вопросы ко мне | 2–3 диагностических вопроса про то, чего НЕТ в данных: намерения, план, коммуникация, что было на экране |

Разделы 6 и 7 закрывают ответ намеренно: вывод инструмента — начало разговора, а
не вердикт. Прежний раздел «Куда копать дальше» просил модель сформулировать
вопросы *от лица игрока*; теперь модель предлагает версии и спрашивает сама, а
раздел «что спросить» стал ненужным дублированием.

**Профиль использует свой набор разделов** (`profile.format.p1`…`p7`): портрет
игрока по выборке → что работает стабильно → главный повторяющийся leak → где игра
ломается по времени → план на следующие матчи → гипотезы → вопросы ко мне. Разбор
по стадиям одного матча здесь смысла не имеет, а «повторяющийся leak» в одиночном
разборе — не имеет.

К правилам профиля добавляются три специфичных: разбирать повторяющееся, а не
отдельный матч (`profile.method.repeating`); помнить размер выборки и не выдавать
наблюдение за закон (`profile.method.sample`); не придумывать таймингов и деталей
боёв, которых в агрегате нет, а называть `match_id` и просить разобрать его
отдельно (`profile.method.no_raw`).

## Уровень игрока (`--mmr`)

Свободная строка: число (`3500`) или бракет (`Legend`). Попадает в две точки —
строку `meta.level` в секции МЕТА и правило `method.calibrate`. Пустая строка =
отсутствие значения.

## Упаковка под модель (`--model`)

[render.py](../dota2coach/render.py). Данные и методика от модели не зависят —
отличается только разметка границ между блоками.

| Модель | Обёртка | Глубина по умолчанию |
|---|---|---|
| `chatgpt` | markdown | `quick` |
| `claude` | XML | `deep` |
| `gemini` | markdown | `deep` |

XML-теги верхнего уровня: `<role>`, `<match_data>`, `<data_limitations>`,
`<player_question>`, `<method>`, `<output_format>`. Внутри тегов остаётся markdown.
Если в группе одна секция, её `##`-заголовок не печатается — имя тега уже говорит,
что это за блок. В группе данных секций много, там заголовки сохраняются.

Дефолтная глубина применяется только когда `--depth` не задан явно
(`render.resolve_depth`).

## Роль (`--role`)

`Policy.role` принимает позиции `1`–`5`. Без флага `Pipeline` берёт
`Player.position_key`, вычисленный нормализатором; явный выбор побеждает
эвристику **только для ★**. Объект `Match` не мутируется, поэтому роли остальных
игроков и повторные экспорты того же матча не меняются.

| Роль | Приоритет оценки | Что не считать главным критерием |
|---|---|---|
| 1 Carry | CS@10, GPM, нетворт, power spikes, урон, late deaths | голый итоговый KDA |
| 2 Mid | XPM, руны, ранний темп, участие, матчап, ротации | только GPM/CS |
| 3 Offlane | инициация, фронтлайн, пространство, полученный урон | минимальное число смертей |
| 4 Soft Support | темп, ассисты, контроль, стаки, вижн, utility | фарм и CS |
| 5 Hard Support | вижн/детект, стаки, лечение, участие, team items | фарм и CS |

Роль одновременно:

* добавляет `method.role.N` в scaffold;
* переопределяет позицию ★ в МЕТА/ДРАФТЕ/ЛАЙНИНГЕ;
* меняет порядок и состав бенчмарков ★;
* формирует секцию `РОЛЕВЫЕ ПОКАЗАТЕЛИ ★`;
* даёт UI список основных focus через `ROLE_FOCUSES`.

OpenDota не отдаёт надёжный save-event counter. Для support показываются
`hero_healing`, teamfight involvement и защитные предметы, а в ограничениях
явно запрещено выводить из них выдуманное число сейвов.

## Язык промпта (`--lang`)

`ru` (эталон), `en`, `uk`. Переключается **весь** промпт: заголовки секций,
подписи внутри строк, названия позиций и объективов, ограничения, скаффолд и
указание модели отвечать на этом языке.

Как это устроено: код не печатает прозу, он отдаёт ключ.

* `normalize.py` не собирает подписи — `Objective` хранит `kind` и параметры,
  `Player` хранит `position_key` и `lane_key`;
* `features.py` отдаёт канонические ключи (`kills.neutrals`, `tf.win`,
  `items.kind.key`) и оговорки парами «ключ + параметры»;
* `bundle.py` подставляет текст из словаря языка.

Метка своего игрока — `★` без букв: она не переводится, иначе разъехалась бы с
легендой в шапке.

Новый язык = один файл в `i18n/` плюс код в `_MODULES`. `i18n.missing_keys()`
сверяет любой язык с русским; офлайн-тест падает при первом же расхождении.

## Заметка игрока (`--note` / `--ask`)

Единственный вход в промпт, который приходит не из OpenDota, а от пользователя.
Объёма экспорта он не меняет — меняет **приоритет разбора**.

| | Без заметки | С заметкой |
|---|---|---|
| Шапка промпта | как есть | + строка «ВАЖНО: ниже есть блок ГЛАВНЫЙ ЗАПРОС ИГРОКА» |
| Перед методикой | ничего | секция `## ГЛАВНЫЙ ЗАПРОС ИГРОКА` (в markdown — в рамке `=`, в XML — тег `<player_question>`) |
| Правила | без первого пункта | первым правилом идёт `method.note_priority` |
| Формат ответа | разделы 1–7 | добавляется раздел 0 «Ответ на главный запрос» |

Правила:

* заметка не встаёт равноправным пунктом ни в один список — иначе она
  растворилась бы среди генеричных требований;
* текст заметки печатается ровно один раз, в своём блоке. В шапке — указатель без
  текста, в правилах и формате — ссылка на блок. Приоритет держится структурой,
  а не повторами;
* рамка `=` рисуется только в markdown: в XML границу задаёт тег;
* пустая строка или одни пробелы = отсутствие заметки, промпт собирается как обычно;
* многострочная заметка сохраняет переносы.

Хранится в `Policy.note` — там же, где `--role`, `--depth`, `--focus`, `--window`,
`--model`, `--lang` и `--mmr`: всё это параметры интента. В режиме профиля заметка
работает точно так же, только раздел ответа называется `profile.format.p0`.
См. [policy.py](../dota2coach/policy.py).

## Матрица секций

Базовый уровень по глубине; `--focus` переопределяет его **абсолютно** — то есть
не только поднимает профильную секцию, но и приглушает непрофильные.

| Секция | quick | deep | laning | fights | farm | draft |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| МЕТА | 1 | 1 | 1 | 1 | 1 | 1 |
| ОКНО (только с `--window`) | 3 | 3 | 3 | 3 | 3 | 3 |
| РОЛЕВЫЕ ПОКАЗАТЕЛИ ★ | 1 | 1 | 1 | 1 | 1 | 1 |
| СТАТИСТИЧЕСКИ НЕОБЫЧНОЕ | 1 | 1 | 1 | 1 | 1 | 1 |
| ДРАФТ | 1 | 2 | 1 | 1 | 1 | **2** |
| СКОРБОРД | 1 | 1 | 1 | 1 | 1 | 1 |
| БЕНЧМАРКИ | 1 | 2 | 1/2 | 1/2 | 1/2 | 1/2 |
| ЭКОНОМИКА | 1 | 2 | 1 | 1/2 | **2** | 1 |
| ПРЕДМЕТЫ | 1 | 2 | 1 | 1 | **3** | 1 |
| РАСКАЧКА | 1 | 2 | 1 | 1/2 | 1/2 | 1 |
| ЛАЙНИНГ | 1 | 2 | **2** | 1 | 1 | 1 |
| БОЙ | 1 | 2 | 1 | **2** | 1 | 0 |
| БАФФЫ | 0 | 1 | 0 | 1 | 0/1 | 0 |
| ТИМФАЙТЫ | 1 | 2 | 1¹ | **2** | 1 | 1 |
| УРОН | 0 | 1 | 0 | **1** | 0 | 0 |
| ОБЪЕКТИВЫ | 1 | 2 | 0 | 1/2 | 1/2 | 0 |

Ячейка `1/2` — фокус не трогает секцию, действует базовый уровень глубины.

Секция отклонений в `_FOCUS_OVERRIDES` отсутствует сознательно: из неё строятся
гипотезы, и приглушать её нельзя ни фокусом, ни окном. Секция окна существует
ровно тогда, когда задан `--window`, и всегда идёт полным логом.

¹ При `--focus laning` тимфайты дополнительно отфильтрованы окном 0–10 мин.

Новые role-aware focus используют ту же шкалу:

| Секция | vision | tempo | initiation | enable |
|---|:---:|:---:|:---:|:---:|
| РОЛЕВЫЕ ПОКАЗАТЕЛИ ★ | **2** | **2** | **2** | **2** |
| БЕНЧМАРКИ | 1 | 1/2 | 1/2 | 1 |
| ЭКОНОМИКА | 0 | 1 | 0 | 0 |
| ПРЕДМЕТЫ | 1 | 1 | 1 | **2** |
| РАСКАЧКА | 1/2 | 1/2 | 1/2 | 1/2 |
| ЛАЙНИНГ | 0 | **2** | 1 | 1 |
| БОЙ | **2** | **2** | **2** | **2** |
| БАФФЫ | 0 | 0 | 1 | 0 |
| ТИМФАЙТЫ | 1 | **2** | **2** | **2** |
| УРОН | 0 | 0 | 1 | 0 |
| ОБЪЕКТИВЫ | 1 | **2** | 1 | 1 |

`vision` поднимает варды/деварды и скрывает фармовые кривые; `tempo` —
лайн, ранний импакт и объективы; `initiation` — бои, контроль и полученный урон;
`enable` — стаки, участие и командные/защитные предметы. Неперечисленные секции
используют базовый quick/deep уровень.

## Тайм-окно (`--window`)

`Policy.window` — пара минут (включительно). Когда она задана, `Policy.level()`
прижимает **каждую** секцию до `SUMMARY`, а секция окна получает `FULL_LOG`.

Это не секция поверх остального, а перераспределение внимания. Единственное
исключение из сжатия — `СТАТИСТИЧЕСКИ НЕОБЫЧНОЕ В ДАННЫХ`: из него строятся
гипотезы, и оно нужно целиком независимо от разбираемого отрезка.

| Сигнал внутри окна | Поле OpenDota | Отличие от обычной секции |
|---|---|---|
| Перевес команды по минутам | `radiant_gold_adv`, `radiant_xp_adv` | без прореживания в 5 мин |
| Все 10 игроков поминутно | `gold_t`, `xp_t`, `lh_t`, `dn_t` | все игроки, каждая минута |
| Убийства | `players[].kills_log` | все игроки, не только ★ |
| Покупки | `players[].purchase_log` | **включая расходники**, порог стоимости не применяется |
| Бои, задевшие окно | `teamfights[]` | всегда поимённо, независимо от `--depth` |
| Объективы | `objectives[]` | включая рутинные |

Расходники внутри окна оставлены сознательно: по ним видно, кто готовился к бою, а
кто фармил. На всём матче это был бы шум, в окне 30–40 — сигнал.

Пустое окно печатается как факт («отрезок был пустым»), а не пустой секцией: иначе
модель начнёт достраивать события. В `ОГРАНИЧЕНИЯ ДАННЫХ` добавляется оговорка о
том, что остальные секции сжаты.

## Статистически необычное в данных

Живёт в [anomalies.py](../dota2coach/anomalies.py). Секция есть при **любом**
фокусе и глубине: в `_FOCUS_OVERRIDES` она сознательно не упомянута, а окно её не
трогает.

Принцип тот же, что и во всём проекте, — не хардкодить предметные знания.
Списка «важных предметов» или «типичных ошибок» здесь нет: он потребовал бы ручного
ведения и всё равно отставал бы от патча и матчапа. Ищем отклонения в самих данных.

| Отклонение | Ключ | Ось | Как считается |
|---|---|---|---|
| Предмет отстал от темпа сборки | `anom.item_lag` | билд | ожидаемая минута = накопленная стоимость / GPM; флаг только если превышение над **медианой** отставания по сборке ≥ 3 мин и факт ≥ 1.15× ожидания |
| Перцентиль внизу распределения | `anom.bench_low` | по метрике | `benchmarks[].pct ≤ 20`; показываем до трёх |
| Перцентиль вверху | `anom.bench_high` | по метрике | `pct ≥ 80`; показываем один, самый крайний |
| Разрыв между метриками | `anom.bench_spread` | файты | размах перцентилей ≥ 45 |
| Провал в доходе | `anom.farm_stall` | фарм | участок ≥ 4 мин после 8-й минуты, где прирост `gold_t` ≤ 0.6 личного среднего |
| Кластер смертей | `anom.death_cluster` | позиционирование | ≥ 3 смерти в окне 5 мин (по `kills_log` врагов) |
| Много времени мёртвым | `anom.dead_share` | позиционирование | `life_state` ≥ 10% матча и ≥ 1.5× медианы остальных |
| Разрыв лайн-эффективности | `anom.lane_gap_*` | линия | \|разница\| ≥ 15 п. против соперников по линии |
| Участие в убийствах на краю | `anom.kp_low` / `anom.kp_high` | файты | ≤ 40% или ≥ 85% от килов команды |
| Быстрый разворот перевеса | `anom.gold_collapse` | файты | окно 5 мин с потерей ≥ 5000 относительного золота |

Медиана в первом пункте — не деталь реализации, а суть метода: без неё у саппорта
с вардами, расходниками и выкупами флагом помечался бы каждый предмет подряд.
Сравнение идёт с **собственной** сборкой, поэтому «поздний BKB» возникает как
следствие, а не как отдельное правило.

Отбор: не больше семи отклонений, сортировка по внутренней severity. Сама severity
в промпт **не печатается** — точность такой оценки мнимая, а игрок читал бы её как
«важность». Метрики бенчмарков фильтруются белым списком: OpenDota отдаёт их
больше, чем у нас есть подписей, и без фильтра в промпт утекал бы маркер
несуществующего перевода.

Оценок в секции нет — только факт и его контекст. Если отклонений не нашлось, это
печатается явно, иначе модель начнёт додумывать аномалии.

## Профиль (кросс-матчевый режим)

Живёт в [profile.py](../dota2coach/profile.py). Отдельный конвейер поверх того же
источника: `DataSource.fetch_player_matches()` → `fetch_match(allow_parse=False)`
для каждого → `ProfileAggregator` → `ProfileBundleBuilder`.

Здесь «сигнал > объём» работает жёстче всего: полных данных матчей в промпте нет
вообще. Это проверяется офлайн-тестом.

| Секция | Из чего считается |
|---|---|
| `ВЫБОРКА` | сколько матчей вошло из запрошенных, фильтры |
| `СРЕДНИЕ ПО ВЫБОРКЕ` | GPM/XPM/CS@10/нетворт, KDA, участие, лайн-эффективность, винрейт, средняя длительность; плюс худший матч по смертям как контекст к среднему |
| `ТРЕНДЫ ПЕРЦЕНТИЛЕЙ` | `benchmarks[].pct` по 6 метрикам: среднее, размах, направление (свежая половина против старой, порог 8 п.) |
| `ПОВТОРЯЮЩИЕСЯ ОТКЛОНЕНИЯ` | тот же детектор аномалий, применённый к каждому матчу; паттерн = ≥ 40% выборки и ≥ 2 матчей |
| `ПРОФИЛЬ ПО СТАДИЯМ ИГРЫ` | `radiant_gold_adv`: **изменение** перевеса за каждые 5 мин, усреднённое по выборке |
| `СОСТАВ ВЫБОРКИ ПО ГЕРОЯМ` | без него средние нельзя читать честно |
| `МАТЧИ ВЫБОРКИ` | по одной строке на матч + оси его отклонений |

Почему изменение, а не уровень перевеса: уровень тянется из предыдущих стадий, и
провал в мид-гейме выглядел бы как провал во всём лейте.

Границы: 2–20 матчей. Меньше двух — это не профиль; больше двадцати — минуты
ожидания на лимите ~1 запрос/сек и усреднение по разным патчам.

**Оговорки, которые уходят в промпт:** это агрегат, а не полные данные; сколько
матчей недоступно; сколько без полного парсинга; сколько позиций смешано в
выборке; сколько патчей она охватывает.

**Защита от вымысла в стадиях.** Поминутные ряды есть только у распарсенных
матчей, поэтому стадии часто опираются на меньшую выборку, чем весь профиль. Если
таких матчей меньше двух, слово «систематически» не употребляется: печатается
таблица и оговорка, что это единичное наблюдение. Стадия считается сравнимой,
только если измерена хотя бы на половине доступных матчей — у долгих игр поздние
корзины пустуют.

## Соответствия: сигнал → поле OpenDota

### МЕТА — тир S, всегда

| Сигнал | Поле OpenDota |
|---|---|
| ID матча, длительность | `match_id`, `duration` |
| Патч | `patch` → `constants/patch` |
| Режим, тип лобби | `game_mode`, `lobby_type` → `constants/game_mode`, `constants/lobby_type` |
| Результат и моя сторона | `radiant_win`, `players[].player_slot` (`< 128` = Radiant) |
| Кто я | `players[].account_id` (или совпадение по имени героя) |

### РОЛЕВЫЕ ПОКАЗАТЕЛИ ★ — тир S

Секция всегда относится только к своему игроку. Состав строки зависит от
эффективной роли:

| Сигнал | Поле / производное |
|---|---|
| CS@10 | `players[me].lh_t[10]` |
| GPM / XPM / нетворт / урон / лечение | одноимённые итоговые поля игрока |
| Участие в убийствах | `(kills + assists) / сумма kills команды`, ограничено 0–100% |
| Ранние киллы | `kills_log.time ≤ 15:00` |
| Late deaths carry | `kills_log` соперников, где victim = ★ и `time ≥ 40:00` |
| Полученный урон / контроль | сумма `damage_taken` / `stuns` |
| Вижн | `obs_placed`, `sen_placed`, `observer_kills`, `sentry_kills` |
| Стаки | `camps_stacked`, `creeps_stacked` |
| Участие и смерти в крупных боях | `teamfights[].players[me]` |
| Utility timings | `purchase_log`, отфильтрованный явным набором командных предметов |

Явный `--role` меняет эту секцию, META и позицию ★ в составе, но не исходные
поля `Player.position_key` других игроков.

### ДРАФТ — тир S

| Сигнал | Поле OpenDota | Уровень |
|---|---|---|
| Пики и баны | `picks_bans[].{order, is_pick, hero_id, team}` | 1 |
| Составы и роли | `players[].{lane_role, is_roaming, net_worth}` → эвристика позиций 1–5 | 1 |

**Ограничение источника.** Реальную хронологию драфта `order` отражает только в
Captains Mode. В all draft / all pick OpenDota отдаёт сначала все пики (`order`
0–9), потом все баны (10–16). Порядок определяется автоматически
(`Match.draft_is_chronological`): если пики и баны чередуются — печатаем один
хронологический список; если сгруппированы — печатаем двумя группами и пишем об
этом в «ОГРАНИЧЕНИЯ ДАННЫХ». Восстанавливать «правдоподобный» порядок по правилам
режима мы намеренно не стали — это был бы домысел, а не данные.

### СКОРБОРД — тир S, всегда

| Сигнал | Поле OpenDota |
|---|---|
| Уровень, K/D/A | `level`, `kills`, `deaths`, `assists` |
| Добивания / денаи | `last_hits`, `denies` |
| GPM / XPM | `gold_per_min`, `xp_per_min` |
| Нетворт | `net_worth` (запасной вариант — последняя точка `gold_t`) |
| Урон, лечение | `hero_damage`, `tower_damage`, `hero_healing` |
| Получено урона | сумма значений `damage_taken` |

### БЕНЧМАРКИ — тир S (мои) / A (все)

`players[].benchmarks.<метрика>.{raw, pct}` — сырое значение и перцентиль 0–1,
который мы печатаем как 0–100. Метрики: `gold_per_min`, `xp_per_min`,
`kills_per_min`, `last_hits_per_min`, `hero_damage_per_min`,
`hero_healing_per_min`, `tower_damage`, `stuns_per_min`.

Для ★ состав и порядок role-aware: carry начинает с GPM/LH, mid — с XPM/kill
impact, offlane — с контроля, supports — с healing/control/participation. Для
позиций 4–5 `last_hits_per_min` и `gold_per_min` исключены как нерелевантные
критерии. В deep бенчмарки остальных игроков остаются универсальными.

### ЭКОНОМИКА: перевес команд и кривые нетворта

| Сигнал | Поле OpenDota | Тир |
|---|---|---|
| Перевес команды по золоту / опыту | `radiant_gold_adv`, `radiant_xp_adv` (знак разворачивается, если я в Dire) | S |
| Переломы — минуты смены знака перевеса | производное от `radiant_gold_adv` | S |
| Пик и провал перевеса | производное от `radiant_gold_adv` | S |
| Моя кривая + кривые вражеских коров | `players[].gold_t` | S |
| Кривые всех десяти | `players[].gold_t` | A |

Ряды прорежены до **1 точки в 5 минут** плюс последняя минута; переломы
перечислены отдельно, поэтому прореживание не съедает сюжет матча. Полный дамп
нетворта по всем десяти игрокам не печатается ни в одном режиме.

### ПРЕДМЕТЫ И ТАЙМИНГИ

Источник — `players[].purchase_log[].{time, key}` плюс `constants/items`
(`cost`, `components`, `qual`).

**Алгоритм отбора.** Идём по логу покупок; встретив собранный предмет, помечаем
его компоненты среди более ранних непоглощённых покупок как «съеденные». Затем
выбрасываем расходники (`qual` содержит `consumable`), рецепты (`recipe_*`) и всё
дешевле порога. Так из лога уходят Iron Branch, Tango, Boots of Speed и Yasha, а
остаются Power Treads и Manta Style — с их настоящим таймингом.

| Кто | Порог | Тир |
|---|---|---|
| Я | от 1000 золота | S |
| Остальные | от 2000 золота | A |
| Я, полный лог покупок | без порога | B (`--focus farm`) |

`aghanims_shard` (1400) включается всегда, несмотря на порог для чужих сборок.

В `РОЛЕВЫХ ПОКАЗАТЕЛЯХ` для позиций 3–5 дополнительно выводятся тайминги
командных/защитных предметов из небольшого явного allowlist (Force Staff,
Glimmer Cape, Mekansm/Greaves, Pipe, Lotus, Blink и т. п.). Это не попытка
угадать назначение любого дорогого предмета.

### РАСКАЧКА СПОСОБНОСТЕЙ

`players[].ability_upgrades_arr` → `constants/ability_ids` → `constants/abilities`.

| Кто | Тир |
|---|---|
| Я + соперники по линии | S |
| Все десять | A |

**Два ограничения источника.**

1. `ability_upgrades_arr` — это **порядок** прокачки без таймингов, и его индекс
   не равен уровню героя (у Phantom Lancer 30-го уровня в массиве 22 записи).
   Поэтому печатаем `#1, #2, …`, а не «уровень 1, уровень 2».
2. У талантов в `constants/abilities` есть только `dname` с неразрешённым
   шаблоном вида `+{s:bonus_rot_slow}% Rot Slow` — числовых значений в OpenDota
   нет вообще. Шаблон срезается (`strip_loc_tokens`), остаётся чистое название
   `талант: Rot Slow`. Подставлять числа неоткуда, и выдумывать их мы не будем.

### ЛАЙНИНГ 0–10

| Сигнал | Поле OpenDota | Тир |
|---|---|---|
| Моя линия и роль | `lane`, `lane_role`, `is_roaming` | S |
| Лайн-эффективность | `lane_efficiency_pct` (у всех — для сравнения линий) | S |
| Мои добивания / денаи по минутам | `lh_t`, `dn_t` (индексы 1–10) | S |
| Соперники по линии | игроки другой стороны с тем же `lane` | S |
| Мои киллы в лайнинге | `players[].kills_log[].{time, key}`, `time ≤ 600` | S |
| Мои смерти в лайнинге | `kills_log` соперников, где `key` = мой npc-герой | S |
| Моё золото / опыт по минутам | `gold_t`, `xp_t` (индексы 1–10) | A |
| Добивания соперников по линии | `lh_t`, `dn_t` соперников | A |

### БОЙ И ЭКОНОМИКА (доп. счётчики)

| Сигнал | Поле OpenDota | Тир |
|---|---|---|
| Лучшая серия, мультикилл | `kill_streaks`, `multi_kills` | A |
| Время контроля | `stuns` | A |
| Стаки лагерей | `camps_stacked` | A |
| Руны | `rune_pickups` | A |
| Поставленные варды | `obs_placed`, `sen_placed` | A |
| Выкупы | `buyback_count` | A |
| Время мёртвым | `life_state["2"]` | A |
| Добито объектов | `neutral_kills`, `ancient_kills`, `tower_kills`, `roshan_kills`, `courier_kills`, `observer_kills`, `sentry_kills` | A |
| APM, пинги | `actions_per_min`, `pings` | **B** |
| Крупнейший одиночный удар по герою | `max_hero_hit.{value, key}` | **B** |

`max_hero_hit` подписан развёрнуто: раньше в промпт уходило «макс.удар 280 по
Disruptor» без объяснения, что это единичный удар, а не суммарный урон.

### ПОСТОЯННЫЕ БАФФЫ — тир A

`players[].permanent_buffs[].{permanent_buff, stack_count, grant_time}` →
`constants/permanent_buffs` → `constants/items` либо `constants/abilities`.

Записи со `stack_count = 0` **выбрасываются**: это не баффы, а отметки «у игрока
есть Aghanim's Scepter / Shard», и их тайминг уже виден в секции предметов. В
разобранном матче из 13 записей осмысленной оказалась одна — `Flesh Heap ×15`.

### ТИМФАЙТЫ

| Сигнал | Поле OpenDota | Тир |
|---|---|---|
| Окно боя, всего смертей | `teamfights[].{start, end, deaths}` | S |
| Кто выиграл бой | сумма `teamfights[].players[].deaths` по сторонам | S |
| Кто погиб | `teamfights[].players[].deaths` (индекс = позиция в `players`) | S |
| Мой вклад | `teamfights[].players[me].{damage, deaths, gold_delta, xp_delta, killed}` | S |
| Поимённая раскладка | `teamfights[].players[]` — участники с уроном или смертями | A |

В сводке бой занимает 1–2 строки вместо десяти. Полная раскладка 13 боёв × 10
игроков — только в `--depth deep` или `--focus fights`.

### УРОН ПО ГЕРОЯМ — тир A

`players[].damage`, отфильтрованный по ключам `npc_dota_hero_*`, топ-5 целей.

### ОБЪЕКТИВЫ — тир S

`objectives[].{type, time, key, unit, team}`.

| Тип события | Что печатаем |
|---|---|
| `building_kill` | кто снёс, что снесено, чьё это было строение, и герой из `unit` |
| `CHAT_MESSAGE_ROSHAN_KILL`, `CHAT_MESSAGE_AEGIS` | Рошан и подбор Aegis |
| `CHAT_MESSAGE_MINIBOSS_KILL` | Тормантор |
| `CHAT_MESSAGE_FIRSTBLOOD` | первая кровь |
| `CHAT_MESSAGE_COURIER_LOST` | курьер (помечен как рутина) |

В `key` лежит **владелец** упавшего строения, а в `unit` — тот, кто его снёс.
Раньше это печаталось как «Radiant: снесена вышка», что читается ровно наоборот;
теперь обе стороны названы явно. `fort` — это трон, а не вышка.

## Сознательно не экспортируем

Поля есть в ответе OpenDota, но в промпт не идут: шум перевешивает пользу.

| Поле | Почему |
|---|---|
| `lane_pos` | агрегированный хитмап координат, не временной ряд — трактовать нечем |
| `obs_log`, `sen_log`, `obs_left_log`, `sen_left_log` | логи вардов; в разборе хватает счётчиков |
| `runes_log`, `item_uses`, `ability_uses`, `ability_targets` | сотни строк низкой ценности |
| `damage_inflictor`, `damage_inflictor_received` | разбивка урона по источникам, нужна редко |
| `cosmetics`, `personaname`, `rank_tier`, `party_id` | к разбору игры отношения не имеют |
| Чат матча | шум |

## Чего в OpenDota нет в принципе

Печатается в секции «ОГРАНИЧЕНИЯ ДАННЫХ», чтобы LLM не додумывала:

* гранулярность рядов — 1 точка в минуту, посекундной нет;
* позиции игроков во времени — только агрегированный хитмап;
* HP по времени и посекундные размены;
* числовые значения талантов;
* тайминги прокачки способностей;
* истинный порядок драфта в all draft / all pick;
* позиции 1–5 — наша эвристика по линии и нетворту, а не факт из источника.
  Для ★ пользователь может явно переопределить её через `--role`;
* надёжный счётчик save events — лечение и защитный предмет являются
  свидетельствами, но не числом сейвов.

Всё это — задача Тир 3 (собственный парсер реплеев). Он подключится как ещё одна
реализация `DataSource` и вернёт тот же `Match`, не задев остальной конвейер.
